## I. Project Overview

DentiSYS is a web-based academic grading and retention monitoring system designed for the College of Dental Medicine at Bicol University that manages student academic grades, retention monitoring, biometric attendance through facial recognition, and report generation. As part of the course requirements in IAS 2 (IT 122), this documentation extends the proposed capstone project system design by integrating a detailed security architecture focused on Module A: Identity & Access Fortification and Module C: API & Perimeter Defense. Additionally, this documentation also includes a VAPT Verification plan and is limited to security architecture design, documentation, and testing plans with no actual implementation, deployment, or live vulnerability testing.

## II. Part 1 — Security Architecture Design

### Module A: Identity & Access Fortification

#### 1. Multi-Factor Authentication (TOTP) Enrollment and Verification Flow Diagram

The DentiSys system improves account security by adding Time-based One-Time Password (TOTP) authentication, based on RFC 6238, to the existing email and password login process, as shown in Figure 1. TOTP was selected instead of SMS-based verification because it does not rely on a mobile network, eliminates additional telecom costs for the Bicol University College of Dental Medicine, and provides better protection against security threats such as SIM-swapping and SMS interception. This authentication method is well suited for faculty members and class secretaries who regularly access the system using university computers or their own mobile devices. 

Before users can log in with TOTP, they need to complete a one-time enrollment process. For Faculty members, enrollment becomes available after the Dean (Admin) approves their account. For Class Secretaries, the process begins when a Faculty member sends an activation invitation to their official Bicol University email address, allowing them to register their account. Once registration is initiated, the server generates a cryptographically secure 160-bit secret. This secret is encoded in Base32, encrypted using AES-256, and stored in the Users table to ensure that its plaintext value is never saved in the database. The server then creates an `otpauth://` provisioning URI and displays it as a QR code, which the user scans using an authenticator application such as Google Authenticator or Microsoft Authenticator. To complete the enrollment, the user enters the six-digit verification code generated by the application. After the code is successfully validated, the system enables multi-factor authentication by setting `mfa_enabled = 1`. It also generates ten single-use recovery codes that can be used if the authenticator application is unavailable. For added security, these recovery codes are stored only as salted hashes rather than in their original form.

When users sign in to DentiSys, the system first verifies whether the entered password matches the stored Bcrypt hash. Once the password has been confirmed, users are asked to provide the six-digit code from their authenticator application. The server decrypts the stored secret and uses the HMAC-SHA1 algorithm to generate the expected TOTP value based on the current 30-second time interval. Since minor clock differences between devices can occur, the system allows a tolerance of one time step before or after the current interval. After both authentication steps are successfully completed, a short-lived JWT access token and a rotating refresh token are issued, as discussed in Module C. If the submitted code is invalid, the failed login attempt is recorded by increasing the account's lockout counter. In addition, recently used time steps are temporarily stored in Redis to prevent the same TOTP code from being reused within its valid time window, reducing the risk of replay attacks.

#### 2. Role-Based Access Control (RBAC) Matrix

Access to DentiSys follows the principle of least privilege, ensuring that users can only perform actions relevant to their assigned roles. Class Secretaries are limited to managing daily block attendance records and submitting attendance override requests. Faculty members are responsible for tasks such as maintaining the student directory, computing grades, scheduling remedial activities, and sending invitations to Class Secretaries. Administrative functions, along with overall system management, are reserved exclusively for the Dean (Admin). Every request made to the system is validated on the server using the role associated with the user's JWT. In addition to role-based authorization, object-level access checks are performed to ensure that Faculty members and Class Secretaries can view or modify only the records and assigned blocks that they are authorized to access.

#### 3. Design Rationale

DentiSys protects user credentials by ensuring that passwords are never stored or verified in plain text. Instead, the system uses the Bcrypt hashing algorithm and memory-hard function designed to resist brute-force attempts. The TOTP authentication mechanism provides an additional layer of security by generating a unique six-digit code through the HMAC-SHA1 algorithm using a shared secret and the current time interval. Since only the generated code is submitted during authentication, the shared secret itself is never transmitted over the network. Likewise, recovery codes are not stored in their original form. Each code is protected using salted hashes so that, even if the database were compromised, the recovery codes could not be used directly by an attacker.

To further secure the system, DentiSys applies Role-Based Access Control (RBAC) to regulate what each user is allowed to do. Every account is assigned permissions based on its designated role, ensuring that users can access only the features required for their responsibilities. For example, Class Secretaries are responsible for recording attendance and submitting attendance override requests, but they cannot compute grades, approve faculty registrations, modify retention policies, or perform other administrative functions. These restrictions help separate responsibilities among users and reduce the possibility of unauthorized actions. The system also performs authorization checks on the server for every request, meaning that permissions are enforced by the backend rather than relying solely on the user interface.

The combination of multi-factor authentication and role-based access control provides stronger overall protection for DentiSys. Multi-factor authentication helps verify that the person signing in is the legitimate account owner, even if the password has been exposed. At the same time, RBAC limits what an authenticated user can access based on their assigned role. As a result, compromising a password alone is not enough to gain full access to the system, and even if a Class Secretary account were compromised, the attacker would still be unable to access administrative features or sensitive system data belonging to the Bicol University College of Dental Medicine.

#### 3. Design Rationale

The API & Perimeter Defense controls implemented in DentiSys establish defense-in-depth across network and application layers. Each security control directly addresses specific risk categories within the OWASP Top 10 (2021):

- **A01: Broken Access Control**: Addressable via server-side Role-Based Access Control (RBAC) middleware, strict object-level authorization checks, and perimeter Extended Access Control Lists (ACLs). Extended ACLs enforce network segmentation on router interfaces, restricting direct MySQL / MariaDB database port access (`tcp eq 3306`) exclusively to authorized backend application servers (`10.10.10.0/24` $\rightarrow$ `host 10.10.20.5`) while dropping unauthorized inter-subnet traffic (Rule 40 & Rule 50).

- **A03: Injection**: Mitigated by enforcing PDO parameterized queries for all data interactions with MySQL / MariaDB, preventing untrusted input concatenation. In addition, incoming request payloads are strictly validated against runtime PHP schemas for length, type, and format prior to controller execution. Contextual output encoding using DOMPurify / HTML escaping neutralizes stored and reflected Cross-Site Scripting (XSS) vectors.

- **A05: Security Misconfiguration**: Mitigated by hardening perimeter web server configurations with TLS 1.3 encryption and mandatory production HTTP security headers (`Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`) configured on the web server/application. Media uploads (biometric vectors, medical certificates) are strictly validated by MIME type/extension, capped at $<2\text{ MB}$, and saved outside the web root to block arbitrary code execution.

- **A07: Identification and Authentication Failures**: Defended by rate limiting the authentication gateway (`/api/auth/login` capped at 5 req/min per IP/account) to block automated brute-force attacks. Session security utilizes short-lived JWT access tokens (15-min TTL) paired with single-use rotating refresh tokens. Every token refresh invalidates the previously issued refresh token by pushing its JWT ID (`jti`) to a server-side Redis blacklist. Account lockouts and token revocation prevent session hijacking and credential-stuffing attacks.

- **A09: Security Logging and Monitoring Failures**: Addressed by integrating automated, immutable audit logs for all sensitive system operations—including grade modifications, attendance overrides, faculty registration approvals, and retention threshold updates—ensuring full accountability and post-incident forensic traceability for the Bicol University College of Dental Medicine.

OWASP Top 10 (2021) Mapping Summary:
- **A01: Broken Access Control** $\rightarrow$ Server-side RBAC, object-level checks, Extended ACL subnet rules.
- **A03: Injection** $\rightarrow$ PDO parameterized queries, PHP schema validation, DOMPurify encoding.
- **A05: Security Misconfiguration** $\rightarrow$ TLS 1.3, production HTTP headers, strict upload file restrictions.
- **A07: Identification and Authentication Failures** $\rightarrow$ Rate limiting, TOTP MFA, Argon2id/Bcrypt, single-use JWT rotation & Redis blacklist.
- **A09: Security Logging and Monitoring Failures** $\rightarrow$ Centralized immutable security activity audit logs.

## III. Part 2 — VAPT Verification Plan

### 3.1 VAPT Test Plan

Scanner(s) to be used and why:
- **OWASP ZAP**: Open-source web application scanner used for automated baseline scanning, passive traffic analysis, active scanning (XSS, SQLi, CSRF), and automated API fuzzing.
- **Burp Suite Professional**: Industry-standard manual intercepting proxy used for deep manual logic flaw testing, JWT payload manipulation, and access control verification.
- **Nikto**: Open-source web server scanner used to audit web server misconfigurations, dangerous default files, and insecure HTTP methods.
- **Nuclei**: Fast, template-driven scanner used for quick targeted scans of known CVEs and security header misconfigurations.
- **Nmap**: Network mapper used to audit perimeter firewalls, verify port exposures, and ensure ACL rules isolate the database subnet (`10.10.20.0/28`).

Scope:
- Web Application Portal (Vite/React frontend used by Dean, Faculty, and Class Secretaries).
- Backend REST API Gateway (`/api/*` endpoints).
- Authentication & MFA services (`/api/auth/*`).
- MySQL / MariaDB database listener (`10.10.20.5:3306`), CCTV stream gateway, and biometric file upload handlers.
- Subnets: App Tier (`10.10.10.0/24`), Admin Subnet (`10.10.30.0/26`), CCTV/IoT Subnet (`10.10.40.0/25`).

Expected finding categories:
- Missing security headers (CSP, HSTS, X-Frame-Options).
- Injectable parameters (SQLi, Stored/Reflected XSS).
- Weak session handling & JWT token replay.
- Broken Access Control / IDOR.
- Rate limiting bypasses on authentication endpoints.
- Server and network misconfigurations.

### 3.2 Manual Test-Case Write-Ups

#### Test Case 1
- **Test Case ID**: `VAPT-TC-01`
- **Objective**: To verify that an authorized user with an Admin/Dean role will only be able to access the Admin/Dean dashboard and view associated analytics and administrative information.
- **Method**:
  1. Prepare authorized test accounts for each of the user roles of DentiSYS.
  2. Log in to DentiSYS using a valid Faculty or Class Secretary account.
  3. Attempt to navigate directly to the Dean dashboard through the application's interface.
  4. If the dashboard is not displayed in the user's navigation menu, attempt to access the protected dashboard route directly.
  5. Observe whether the system allows the user to load the Dean dashboard.
  6. Using an authorized request inspection tool in the test environment, verify whether a lower-privileged account can request the Dean dashboard or its associated analytics API endpoints.
  7. Repeat the test using the authorized Dean account.
  8. Verify that the Dean account can access the dashboard and its permitted resources.
- **Tools**: Test accounts representing the defined system roles, DentiSYS authorized test environment, OWASP ZAP or Burp Suite for authorized request inspection, Browser Developer Tools.
- **Success Criteria**:
  - The test is successful if:
  - Faculty and Class Secretary users cannot access the Dean dashboard.
  - Direct navigation to the protected dashboard route is rejected.
  - Requests to Dean-only analytics or report endpoints are rejected by the backend.
  - Changing the URL or client-side request does not grant access to the dashboard.
  - The authorized Dean account can successfully access the dashboard.
  - The system does not expose Dean-only analytics or student information to unauthorized users.
- **Related Module**: Module A: Identity & Access Fortification

---

#### Test Case 2
- **Test Case ID**: `VAPT-TC-02`
- **Objectives**: To verify that the proposed system’s API does not allow access to student grade information when a request is made without a valid authentication token.
- **Method**:
  1. Use an authorized DentiSYS test environment with mock student data.
  2. Identify the API endpoint used to retrieve student grade records.
  3. Attempt to request the endpoint without a JWT.
  4. Observe the server response.
  5. Repeat the request using an invalid or expired JWT.
  6. Repeat the request using a valid JWT belonging to an authorized user.
  7. Compare the responses.
- **Tools**: DentiSYS authorized test environment, OWASP ZAP or Burp Suite, Browser Developer Tools.
- **Success Criteria**:
  - The test is successful if:
  - Requests without a JWT are rejected.
  - Requests with an invalid or expired JWT are rejected.
  - No student grade information is returned to unauthenticated users.
  - A valid and authorized user can access the permitted grade records.
  - The API returns an appropriate authentication or authorization error.
- **Related Module**: Module C: API & Perimeter Defense
