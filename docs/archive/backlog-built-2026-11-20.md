# Backlog items built on 2026-11-20 (9.23, 9.24, 9.26, 12.8)

Full text and Owner decisions of these items as they stood in the [product backlog](../PRODUCT_BACKLOG.md) when they were built. Implemented behaviour is in [spec.md](../../spec.md) and [features.md](../features.md).

- **9.23** Wrong recovery code on the 2FA sign-in page shows "A server error occurred. Try again later." (Owner, 2026-11-19, typed random characters). Real server bug, not only wording: `mfa_runtime_recover` ([backend/app/mfa_runtime.php](../backend/app/mfa_runtime.php) line 446) calls `mfa_normalize_recovery_code`, which throws `InvalidArgumentException` for anything that is not 32 hex characters; `handle_mfa_recover` only catches `MfaException`, so it falls through to the generic handler: HTTP 500 and an `error_log` line for what is a user typo. The authenticator-code path is fine (the form rejects non-6-digit input, and a wrong 6-digit code returns 400 "Invalid verification code."). Fix: treat a malformed recovery code as "Invalid recovery code." (400, same as a wrong one, so it still counts as a failed attempt and leaks nothing). Needs a `tests/backend` test that posts a malformed recovery code and expects 400. Then check the other MFA forms (enrolment, disable, regenerate) for the same gap, and the page's mapped message for 400/429.
- **9.24** 2FA "Remember this device" (Owner, 2026-11-19). Contract approved after `/grill-me` (Owner, 2026-11-19); ready to build (~1.5–2 days), starting with a `ui-fix-demo` Stage 1 look demo.
  - Rule: on the 2FA code step at sign-in, an unchecked "Remember this device for 30 days" box sits between the code field and Verify, no help text. Ticked, that browser skips the code at sign-in for 30 days from that moment (fixed, not extended by later sign-ins). The password (or Google) step is always required. It skips only the sign-in code: in-app actions that ask for a code today (turning 2FA off, regenerating recovery codes, changing name) still ask.
  - Who: every account with 2FA on, Students, Secretaries, Faculty, the Dean and the Superadmin included. Not shown during the Superadmin's first 2FA setup. Hidden on the recovery-code path; switching back to the app code shows it again, unticked.
  - One browser remembers one account: a later tick by another account replaces it. Normal sign-out keeps it. When the 30 days end the code step simply shows again, no message. No email; audit log only.
  - Stops working on: password change or reset, 2FA reset, turning 2FA off or on, recovery-code regeneration, sign-out everywhere, deactivation, an email move, a Dean handover, and "Forget my trusted devices". The first group already raises `token_version` (`auth_invalidate_account`), so a row stores the account's `token_version` and stops matching; 2FA off/on, regeneration and the button revoke the rows.
  - Profile (every role, own account, [MfaSettingsCard.tsx](../frontend/src/components/MfaSettingsCard.tsx)): "Remembered devices: N" and a "Forget my trusted devices" button with a confirmation ("Forget all remembered devices? You'll enter your code at the next sign-in on each one."), no code needed, disabled at 0. The Superadmin has no per-person forget; its Sign out everywhere and Reset 2FA already do it.
  - Data: migration `069_mfa_trusted_devices.sql` (user_id, token_hash SHA-256 unique, token_version, user_agent ≤255, created_at, expires_at, last_used_at, revoked_at, revoked_reason); safe with the previous images. Cookie `trusted_device`: HttpOnly, SameSite=Lax, `Path=/api/auth`, Secure on HTTPS, Max-Age 30 days; a bad, expired or other-account cookie is ignored and cleared.
  - API: `POST /api/auth/mfa/verify` takes `remember_device` (default false); `/api/auth/login` and the three Google sign-in paths (`GoogleAuthController.php`, each calls `auth_issue_two_factor_challenge`) skip the challenge for a valid cookie and return the existing direct-login response; `GET /api/auth/mfa/settings` adds `trusted_device_count`; new `POST /api/auth/mfa/trusted-devices/forget` returns `{ "forgotten": N }`, 401 when signed out.
  - Audit: device remembered; the usual sign-in success row with "2FA skipped on a remembered device"; trusted devices forgotten (count and reason).
  - Spec line to add to AUTH-006 after "…cannot be turned off." (Owner-approved wording, applied in the feature commit): "A user with 2FA, the Superadmin included, may tick "Remember this device for 30 days" on the 2FA code step at sign-in (not when using a recovery code); that browser then skips the code at sign-in for 30 days from that moment, never the password or Google step, and one browser remembers one account at a time. A remembered device stops working on password change or reset, 2FA reset, turning 2FA off or on, recovery-code regeneration, sign-out everywhere, deactivation, an email move, a Dean handover or "Forget my trusted devices" in Profile."
  - Tests: `tests/backend` (skip only with a valid same-account cookie, each revocation, bad cookies fall back), `tests/database` (migration), mocked `e2e` (box, recovery path, Profile button), `e2e/live` (tick, sign out, sign in without a code).
  - Ships before 12.8; 12.8's 2FA step reuses it.
- **9.26** "Remember me" at sign-in (Owner, 2026-11-20). Today there is no such box: the refresh cookie is persistent, so closing the browser does not sign out, but every session ends after 30 minutes without activity (AUTH-007, 2026-11-11) and after 7 days at most. Decided:
  - An unchecked "Remember me for 7 days" box under the password field on `/login` only; it also applies when the user signs in with Google from that page, and carries through the 2FA step.
  - Unticked: the refresh cookie becomes a browser-session cookie (no Max-Age), so closing the browser signs out; the 30-minute idle sign-out stays. (A browser set to restore the previous session may keep it; that is the browser's choice.)
  - Ticked: signed in for 7 days from sign-in (today's absolute limit, not extended by use), even after closing the browser, with no 30-minute idle sign-out. After 7 days the password is asked again.
  - Separate from 9.24 (Owner, 2026-11-20: keep 7 and 30): ticking both means no password and no code for up to 7 days, then the password but no code until the device's 30 days end.
  - Every role except the Superadmin (Owner, 2026-11-20: the Superadmin's password is asked at every sign-in). The Superadmin page (12.8) has no box, its sessions are always unremembered (browser-session cookie, 30-minute idle sign-out), and the server refuses a remembered session for the Superadmin even if one is requested. 9.24's "Remember this device" still skips only the Superadmin's code. Sign-out, sign-out everywhere, password change or reset, deactivation and every other action that ends sessions today still ends a remembered session.
  - Build: the session records whether it is remembered (additive migration, numbered after 9.24's `069`); the server's idle check (`AUTH_IDLE_TIMEOUT_SECONDS` in [auth.php](../backend/app/auth.php)) and the frontend idle tracker ([AuthContext.tsx](../frontend/src/context/AuthContext.tsx)) skip remembered sessions; `build_refresh_cookie_header` ([security.php](../backend/app/security.php)) omits Max-Age for unremembered ones. Audit: the sign-in success row says whether "Remember me" was ticked.
  - Spec: amend AUTH-007's 2026-11-11 idle rule (propose the exact line with the build, apply with the Owner's OK). Tests: `tests/backend` (idle skip only for remembered sessions, the Superadmin never remembered, cookie with and without Max-Age, ended by each session-ending action), mocked `e2e` (box on `/login`, none on the Superadmin page, the frontend idle tracker), `e2e/live` (after a ticked sign-in the browser's refresh cookie has an expiry 7 days out; after an unticked one it is a session cookie).
- **12.8** Superadmin sign-in page (Owner, 2026-11-19). Decisions settled with the Owner (2026-11-19); build after 9.24 (~1 day), with a `ui-fix-demo` demo of the page.
  - Address `/superadmin/sign-in` (not `/admin/login`: the Dean's and Superadmin's pages already use `/admin/...`); linked from nowhere, `noindex` for search engines.
  - The page copies `/login` ([SsoLogin.tsx](../frontend/src/pages/auth/SsoLogin.tsx)) with the heading "Superadmin Sign In" and no Sign up, class-join or Student links; it keeps "Forgot password?" (same reset flow) and "Sign in with Google".
  - Password and Google sign-in on the shared `/login` refuse the Superadmin; the Superadmin page refuses every other role. A refusal looks and counts exactly like a wrong password: the same "Invalid email or password." message, the same sign-in rate limit, and a failed-sign-in audit row with the reason "wrong sign-in page" (shown in the Superadmin's failed sign-ins). For Google sign-in the refusal is Google's existing unknown-account answer, "No existing DentiSYS account was found." (404), not the password message (Owner, 2026-11-20).
  - Required authenticator 2FA (first-sign-in setup included) is unchanged; "Remember this device" (9.24) works on this page's 2FA step.
  - After the Superadmin sets its first password (`/activate-faculty`, from the server script's email) or resets it (`/reset-password`), the page sends it to `/superadmin/sign-in` instead of `/login`; the server tells the page from the link's account.
  - Already signed in: opening `/login` or `/superadmin/sign-in` goes to the role's home page, as today.
  - Not chosen (Owner, 2026-11-19): removing Google for the Superadmin, passkeys, a shorter idle timeout.
  - The sign-in requests (password and Google) carry which page they came from, so the server can refuse by role; a request without it is treated as the shared `/login`.
  - Spec change (AUTH, propose the exact line when building, apply with the Owner's OK), then build: backend role check on both sign-in paths, frontend route and page, link redirects, tests in `tests/backend` (each refusal is a 401 like a wrong password and is rate limited) and `e2e`.
