# DentiSys PostgreSQL Database

This directory is the single source of truth for the DentiSys PostgreSQL schema. Docker initializes a new database with `init.sql`, then runs every ordered migration in `migrations/`.

```text
database/
├── README.md                 This guide
├── init.sql                  Creates the migration ledger
├── apply-migrations.sh       Creates the application role and applies migrations
├── pgadmin-servers.json      Development pgAdmin connection definition
├── migrations/               Ordered PostgreSQL schema and reference-data changes (NNN_description.sql)
├── seeds/                    Manual development-only data
│   ├── development-demo.sql        Fictional demo data (generated)
│   ├── generate_development_demo.py  Generator for development-demo.sql
│   └── fix-hashes.sql              Password-hash fix for the demo accounts
├── reports/                  Read-only review queries
└── archive/mariadb/          Superseded MariaDB files; not used at runtime
```

`migrations/` holds the whole schema history, `001_baseline_schema.sql` through the latest numbered file; list the folder for the current set. Names are `NNN_lowercase_description.sql` with a unique three-digit prefix (checked by `tests/documentation/doc_contract_test.php`), applied in order and recorded in `_schema_migrations`.

## Migration rules

Five-part names and other composite inputs (spec.md ID-002) require explicit mappings, additive migrations, safe backfills, and compatibility handling. Inspect and reuse the existing structured-name migrations before adding new ones.

- Add a new, ordered `NNN_description.sql` file for every schema or reference-data change.
- Never edit a migration that has been applied to a shared environment; create a follow-up migration instead.
- Run `.\scripts\migrate.ps1` after pulling new migrations into an existing development database.
- Fresh PostgreSQL volumes apply all migrations automatically.
- Run `.\scripts\check-postgres.ps1` for the disposable PostgreSQL integration stack and live checks. It imports the manual demo seed twice to verify unchanged counts, usable accounts, and aligned sequences, then removes only its separate project and volume; development data is never reset.

The legacy MariaDB schema, reset scripts, demo seed, and historical migration chain are preserved under `archive/mariadb/`. They are not supported by the current runtime.

## Development demo data

`seeds/development-demo.sql` contains fictional demo users, courses, classes, students, grades, remedial progressions, and attendance history. It is intentionally not a migration and is never run automatically. It is generated by `seeds/generate_development_demo.py`; edit the generator and regenerate, never the SQL.

Load it into a database without students (see the root README, section A6). It makes no schema changes and never drops, truncates, updates, or deletes data; on a database that already has students it inserts nothing. Accounts are listed in [docs/demo-accounts.md](../docs/demo-accounts.md).

## Dean-defined academic terms

The `academic_terms` table (migration `046_academic_terms.sql`) holds Dean-owned dates keyed by school year and
canonical semester (`1ST`, `2ND`, `Summer`). Classes link through their
school year and semester; they carry no dates of their own. Dates use
Asia/Manila and remain valid through the end date. The application serializes
term mutations, class creation and biometric enrollment finalization to enforce
uniqueness, date order, overlap and delete-in-use rules safely.

Biometric validity remains in `biometric_profiles.reference_expires_on` (DATE).
The nullable `reference_term_id` and `reference_cs_id` record its source. A Dean
date edit updates unexpired references for Students with an active class in that
term inside the same audited transaction, recalculating the latest resolved end
among active classes and recording its term/class provenance. This includes
legacy references without provenance. A past end date leaves the material intact
until the expiry run; today remains valid through today. Copying February 29
uses February 28 in the next non-leap year. Copied dates are a starting point for Dean review.

## Computed retention only

Retention status is computed (migration `048_computed_retention_only.sql`): `remedial` when the final grade is 2.50 or worse, else `active`; `archived` is stored, `cleared` is derived on read. There is no stored `warning`/`critical` state and no manual override; the old override columns remain, set to NULL, and `audit_logs` keeps their history.
